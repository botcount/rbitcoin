# Core-class JSON-RPC (rbitcoin)

`params` may be a JSON **array** (positional) or **object** (Core named
keys such as `blockhash`, `verbosity`, `txid`, `hexstring`). Missing
required keys are `-32602`; unknown named keys are `-8`.

rbitcoin serves a **documented subset** of Bitcoin Core JSON-RPC over plain HTTP.
A new method is documented in this file in the same change.
This is **not** full Core parity: no wallet, no `createrawtransaction` /
`signrawtransactionwithkey` / `createmultisig` / `sendtoaddress` (those
live only on the Core-functional test proxy, backed by Esplora).
`decoderawtransaction` / `decodescript` / `validateaddress` are a **node
subset** (table below). Official Core dialect scripts (`rpc_decodescript.py`,
`rpc_validateaddress.py`, `rpc_invalid_address_message.py`) stay inventory
`rpc-dialect`; the functional harness does not intercept those names.
`getblocktemplate` / `getmininginfo` are a miner-backend (no stratum). Address history is **Electrum / Esplora** with `--sh-index`.

## `getnetworkinfo.version`

`version` defaults to the integer **190000**, Bitcoin Core 0.19.0's
`CLIENT_VERSION` (`10000 * 19` in Core's 0.x packing). Typed RPC clients
compare this field when they choose a response shape. Below 190000,
`bitcoincore-rpc`'s `get_blockchain_info` requires the pre-0.19
`bip9_softforks` map and a `softforks` array, then returns
`UnexpectedStructure` on our object. At 190000 it deserializes the
modern object (`softforks` may be absent; `warnings` may be a string or
an array).

190000 is an RPC shape floor:

- `subversion` stays `/rbitcoin:<semver>/`, plus any `--ua-comment`.
  That string is the software version.
- `protocolversion` stays **70016**, the same integer on the P2P
  `VERSION` message. Peers negotiate with that, with service flags, and
  with the handshake messages. They do not read this field.
- The floor is not derived from the crate semver. Packing `0.7.99` with
  Core's post-22 formula yields 799, which sits under every client
  gate. Packing a later rbitcoin `19.0` or `22.0` the same way would
  collide with a real Core `CLIENT_VERSION`.

The default stops at 0.19. A higher integer tells those clients that
later Core RPC is present, including descriptor-wallet calls from 0.21
(`210000`). It does not change what this node serves or what peers
accept.

`--rpc-client-version N` (conf `rpc_client_version=`, `1` through
`1000000`) sets only the reported integer. Leave the default unless a
client refuses to start below a newer floor. Bark's captaind requires
`310000` because Core 31 added the `getmempoolentry` chunk fields, which
this node already returns.

## Operator knobs

| Knob | Default | Meaning |
|------|---------|---------|
| `--rpc` / conf `rpc=` | **off** | Unix JSON-RPC `{datadir}/rpc.sock` (mode 0600; filesystem auth) |
| `--rpc-socket PATH` / conf `rpc_socket=` | **off** | Bind the unix socket at PATH (mode **0660**, group may connect) instead of `{datadir}/rpc.sock`. Implies `--rpc`. For a client running as another user, such as mempool's Node. |
| `--rpc-listen [ADDR]` / conf `rpc_listen=` | **off** | TCP JSON-RPC; omit ADDR → `127.0.0.1` and Core-matching port (8332 / 18332 / 48332 / 38332 / 18443; testnet5 18352). Implies `--rpc`. |
| `--rpc-token-file PATH` | `{datadir}/rpc.token` | CSPRNG hex token; TCP `Authorization: Bearer`. Created mode 0600. An existing file must be owner-only on Unix (group or world bits refuse startup). The node does not chmod it. Delete a wider file and start again: a new token is minted only when the file is gone or zero-length. chmod 0600 keeps a secret that may already have been readable. Windows has no mode bits |
| `--rpc-cookie-file PATH` / conf `rpc_cookie_file=` | **off** | Existing Core-format `username:password` file (no trailing newline) accepted as TCP HTTP Basic in addition to Bearer; it is never created or logged |
| `--rpc-cookie-perms owner\|group\|all` / conf `rpc_cookie_perms=` | **owner** | Widest Unix mode the cookie file may have. `owner` is 0600. `group` is at most 0640 (group read; group write refuses startup). `all` is at most 0644. The node never chmods the file. Windows has no mode bits, so the flag is ignored there. NixOS `services.rbitcoin.rpc.cookiePerms` (default unset, so the unit argv omits the flag) |
| `--sh-index` | **off** | Class B scripthash for Electrum/Esplora address history. RPC by height/hash/txid does not need it |
| `--block-filter-index` | **off** | BIP158 basic. IBD seals them when the flag is on from the start. A later enable still materializes after catch-up. `NODE_COMPACT_FILTERS` is advertised once filters first reach the tip (`getnetworkinfo` lists `COMPACT_FILTERS`), then for the life of the process. `getblockfilter` serves a sealed height, one block whose parent filter is already sealed, and a stale branch back to that sealed fork point. An unsealed best-chain gap is refused. `/rest/blockfilter/` and P2P still serve only heights the watermark covers. Independent of `--sh-index` |
| `--rpc-work-queue N` | **16** | In-flight HTTP RPC (Core `-rpcworkqueue`). One POST is one slot (a JSON-RPC array is still one slot). Full permit is HTTP **503** `Work queue depth exceeded`. **0** is the default queue of 16. The call holds that slot while it waits for a `--store-read-budget` permit. A call that does not read the store, including `getblockcount`, does not take that permit. `waitforblock`, `waitforblockheight`, `waitfornewblock`, and a `getblocktemplate` long-poll (a non-null `longpollid` in template mode; proposal mode does not wait) do not hold the work-queue slot or the disk permit while they wait. A `getblocktemplate` with no `longpollid` keeps the slot and takes it before any store read. The template build reads the tip with no disk permit, takes one permit, and reads the tip again without waiting on connect. It keeps that permit for the header reads only when both reads match, then drops it before transaction selection, so a block connect does not pin that permit and a store read can run during selection. After a long-poll, the next call in that POST waits for a work-queue slot. A POST that has not run a call is still HTTP 503, including a long-poll, and that 503 is before the tip poll. `--store-read-budget N` (`store_read_budget=`) overrides `--datadir-hdd`. Omitted or `0` is 1 on `--datadir-hdd`, otherwise one less than the core count, minimum 1 |
| `--rpc-client-version N` / conf `rpc_client_version=` | **190000** | Integer `getnetworkinfo.version` reports (`1`–`1000000`). Adds no RPC and changes no other field. Bark captaind needs `310000`. NixOS `services.rbitcoin.rpc.clientVersion`. See [getnetworkinfo.version](#getnetworkinfoversion). |
| `--rest` / conf `rest=` | **off** | Unauthenticated `/rest/` on the RPC listener. Own queue, same depth as `--rpc-work-queue`'s default. The body is read before that permit is taken. Built replies not yet written share a 64 MiB budget across all connections; a reply holds its bytes until it is written or its connection closes, and one larger than 64 MiB takes the whole budget. While the budget is spent, a new request is HTTP **503** `Work queue depth exceeded` before anything is built. A built reply whose bytes are not free waits up to 30 s for them, ahead of later requests, and holds its queue slot meanwhile; then it is that 503. Core has no such budget. Without the flag those paths are 404. |

TLS is external (reverse proxy). Unix socket needs no HTTP header. TCP is
Bearer-authenticated (`{datadir}/rpc.token`) and, only when `--rpc-cookie-file`
is configured, also accepts Core cookie HTTP Basic. `GET /rest/…` is on the same
binds only when `--rest` is set. TCP `/rest/` skips Bearer, matching Core. Routes: `chaininfo.json`,
`blockhashbyheight/<height>.<bin|hex|json>`, `headers/<count>/<hash>.*`,
`block/<hash>.*`, `block/notxdetails/<hash>.*`, `tx/<txid>.*` (chain and
mempool), `mempool/info.json`, `mempool/contents.json`, `getutxos.json`
(confirmed spentness, plus the mempool overlay `gettxout` uses when the path
includes `checkmempool`), `deploymentinfo.json`, and
`blockfilter/basic/<hash>.*` when `--block-filter-index` is on and that height is sealed. A later height is “still in the process of being indexed”, not an empty filter.
No wallet routes. Broadcast and fees stay `POST /`.

TCP and the Unix socket each have a 256-connection cap, so TCP clients
cannot lock out the local socket. A `401` reply closes its connection. Each
HTTP header and request body must finish within 30 seconds; waiting for the
next keep-alive request uses the same header deadline. Expiry closes the
connection and releases its slot. These read deadlines do not limit
execution of a complete RPC request, including long-poll calls. A reply
write that makes no progress for 30 seconds closes the connection too, and
so does a reply whose writes spend longer blocked on the socket, in total,
than 30 seconds plus one second per 16 KiB written. The
deadlines are fixed, with no operator knob.
Each JSON-RPC body is one JSON value and a trailing newline. Object keys
are `jsonrpc` (2.0 only), then `result`, then `error`, then `id`, and a
key the response does not carry is omitted.

The Core-functional proxy still
speaks TestNode cookie + HTTP Basic on the public port and forwards Bearer
to the node. Mixed AuthServiceProxy `{args: […], maxfeerate: …}` is expanded
to a positional list in that proxy (`echo` mixed `{args, argN}` stays on the
node).

### curl example (unix socket, no HTTP auth)

```bash
# After node start with --rpc (binds {datadir}/rpc.sock, mode 0600)
curl --unix-socket datadir/rpc.sock --data-binary \
  '{"jsonrpc":"1.0","id":"1","method":"getblockcount","params":[]}' \
  -H 'content-type: application/json' http://rpc/
```

### curl example (TCP Bearer)

```bash
# After node start with --rpc-listen (default 127.0.0.1:8332 on mainnet)
TOKEN=$(cat datadir/rpc.token)
curl -H "Authorization: Bearer $TOKEN" --data-binary \
  '{"jsonrpc":"1.0","id":"1","method":"getblockcount","params":[]}' \
  -H 'content-type: application/json' http://127.0.0.1:8332/
```

### rbitcoin-cli

`--datadir` (default `./datadir`) prefers `{datadir}/rpc.sock`.
`--rpc-socket PATH` talks to a node started with `--rpc-socket PATH`. TCP uses
`--rpc-url host:port` (plain HTTP; no scheme). An IP is a strict address
(`10.0.0.1`, `[::1]`); leading zeros and hex forms are rejected. When the flag is omitted and no
socket is present, the client uses `127.0.0.1` and the network RPC port. Bearer
comes from `{datadir}/rpc.token` or `--rpc-token-file`. Prints the JSON-RPC
`result` (strings unquoted). `--stdin` reads extra arguments from standard input, one per line until EOF,
appended after the command-line arguments (Core-compatible; for values that
should not appear in the process list). `--rpcwait` retries a refused connection once a second until `--rpcwaittimeout N`
seconds have passed (default 30, `0` for no limit).
`--rpcclienttimeout N` is how long one socket read or write may wait before the call
fails: 900 seconds by default on TCP, no limit by default on the unix socket, `0` for no limit.
The connect and the host name lookup are bounded too, by that timeout or by what is left of `--rpcwait`, whichever is shorter.
A negative value is refused (Core reads it as no limit).
`--named` takes `name=value` arguments and sends them as a JSON object instead of a positional array.
`--getinfo` prints a Core-style chain/network summary (no wallet section).
Every option also takes Core's single dash: `-rpcwait`, `-named`, `-stdin`, `-getinfo`,
`-datadir=PATH` or `-datadir PATH`, `-rpcclienttimeout=0`; `-help` and `-version` too, besides `-h` and `-V`.
Core options this client lacks (`-rpcport`, `-rpcuser`) are still refused as unknown.
Unlike Core, options are read anywhere before `--`, so a parameter spelled like an option (`-named`) goes after `--`;
a negative number (`-1`) stays a parameter. A switch takes no value: `-rpcwait=1` and Core's `-norpcwait` are refused.

```bash
rbitcoin-cli --datadir datadir getblockcount
rbitcoin-cli --network regtest --rpc-url 127.0.0.1:18443 getblockchaininfo
```

## shindex matrix

| Capability | `shindex=0` (default) | `shindex=1` |
|------------|----------------------|-------------|
| IBD, tip follow, P2P, mempool relay | Yes | Yes |
| Node JSON-RPC (by height/hash/txid) | Yes | Yes |
| Electrum / Esplora listen | Start; address methods fail closed (`scripthash index disabled`) | Yes after SH tip-ready |
| SH run enqueue / tip bulk | **Skip** | On |

Tip-follow readiness is **independent** of scripthash materialize. Electrum/Esplora
still wait for durable SH when shindex is on.

## Manual bans (`setban` / `listbanned` / `clearbanned`)

`setban <subnet> <add|remove> (bantime) (absolute)` bans an IPv4/IPv6
address or CIDR subnet, or an onion (`.onion`) / I2P (`.b32.i2p`) identity,
which is banned as an identity on any port. A prefix wider than /8 (IPv4)
or /16 (IPv6) is refused.

- **Persistence.** Manual bans live in `{datadir}/banlist.json`, in Core's
  `banned_nets` shape. The file is rewritten on every change (a synced
  temporary file renamed over the old one, so a crash cannot leave an
  empty list behind) and reloaded at startup; entries whose time has run
  out are dropped on load.
- **Expiry.** `bantime` is seconds from now; omitted or 0 means the
  default 86400 (24 hours). With `absolute` true, `bantime` is a unix
  time instead, and one in the past is refused with `-8` ("Error:
  Absolute timestamp is in the past") rather than stored already expired.
- **Enforcement and precedence.** Adding a ban disconnects every live
  session it matches, including a catch-up (IBD) session, which the sync
  loop drops on its next pass. A banned source is refused at inbound accept and a
  banned target is refused before an outbound dial, until the ban expires
  or is removed. A ban takes precedence over `addnode`, `--connect`, and
  `--trust-peer`: a banned peer is disconnected and refused even if it
  was added by hand or is trusted.
- **Loopback.** A manual ban matches loopback: `setban` can ban
  `127.0.0.1` or `::1`. This is Core parity (Core's own ban tests ban
  `127.0.0.0/24`) and differs from automatic discouragement, which never
  records a loopback peer.
- **Overlay identities.** An onion/I2P ban is enforced before an outbound
  dial to that identity and against live outbound sessions to it. An
  inbound connection from a Tor/I2P peer arrives through the local proxy
  and is seen as a loopback connection, so an overlay ban cannot match it
  at accept; banning the proxy's loopback address instead would ban every
  overlay peer at once.
- **Clearing.** `setban <subnet> remove` lifts one ban (`-30` when the
  target is not banned); `clearbanned` drops every manual ban and
  persists the empty list. `listbanned` lists manual bans only. Automatic
  discouragement for misbehavior is a separate in-memory set: these
  methods neither list nor clear it, and it is gone at restart.
